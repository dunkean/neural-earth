REVUE SOL XHIGH — CORRECTIFS DU PRÉCHAUFFAGE, PASSE R5
Verdict : APPROVE pour les quatre correctifs demandés en R4. Aucun défaut bloquant de cohérence numérique ou de cycle de vie trouvé dans cette passe statique. La validation d'un gain global et les gates physiques finales restent séparées.

P0 — La signature envoyée au modèle base reste celle du checkpoint : entrée `[N,5,64,64]`, labels `[N]`, condition tensorielle `[N,58]`, dtype et device des poids (terrain_cuda_graphs.py:181-204 ; base_model/config.json ; terrain_inference.py:328-351). Le test CUDA TinyBase annoncé par l'intégrateur capture les seize formes BF16, rejoue des entrées aléatoires dynamiques et compare les octets eager/graph ; avec max_buckets=4, il vérifie que seules les quatre dernières formes restent, et avec budget nul que le modèle n'est pas appelé (test_terrain_nn_math.py:13-43). Ce test sonde les buffers et l'éviction du wrapper, pas le checkpoint ni les fenêtres physiques finales. Les huit sorties physiques, le SNR et l'identité des sources doivent encore être validés après stabilisation. Aucun test GPU lancé par moi.

P1 R4 résolu — `prewarm_base_forms` inspecte désormais `_buckets` sous son verrou et publie `requested_forms`, `retained_batches`, `forms` et `fully_warmed` (terrain_cuda_graphs.py:205-210). Une limite de buckets ou de mémoire qui évince des tailles ne peut donc plus se faire passer pour seize graphes retenus. `CudaGraphModel.stats()` prend le même verrou avant d'itérer les dictionnaires et de copier les erreurs (terrain_cuda_graphs.py:173-179) ; les demandes `/api/status` peuvent lire un snapshot stable pendant le thread de préchauffage. Le préchauffage conserve les garde-fous de capture, le contrôle torch.equal, l'éviction synchronisée et le fallback eager existants (terrain_cuda_graphs.py:71-171).

P1 R4 résolu — Le warmup optionnel base capture son exception et renvoie `state='failed', fully_warmed=False` sans jeter les poids chargés ; le nombre d'appels CUDA de startup est exposé séparément (terrain_server.py:230-238). Le bloc de startup vide le store dans `finally`, même si `sample_elevation` ou le warmup échoue, puis peut déclarer le modèle prêt lorsque seule l'option base a échoué (terrain_server.py:1230-1250). J'ai exécuté le test CPU `ProtocolTests.test_optional_base_prewarm_failure_is_reported_without_discarding_model` : il passe, avec erreur injectée et compteur de startup nul (test_terrain_navigation.py:434-442). Un test de `warm_models` lui-même avec erreur injectée avant/après base compléterait le contrôle du `finally` ; cette fonction est actuellement locale à `__main__`, ce qui rend son exécution unitaire indirecte.

P2 — La déclaration `fully_warmed` regarde actuellement la seule forme de `x`, pas la clé entière du graphe (terrain_cuda_graphs.py:206-209). Un bucket déjà présent avec `x=[N,5,64,64]` mais autre dtype/device, labels ou condition pourrait être compté à tort ; des tailles hors de `1..limit` pourraient inversement faire échouer l'égalité malgré toutes les tailles voulues. Le chemin serveur usuel produit la même signature pour toutes les formes et le prototype rapporté indique seize buckets conservés, donc je ne classe pas ce point bloquant pour ce déploiement. Comparer les clés complètes attendues via `CudaGraphModel._key` et ajouter un test de bucket homonyme incompatible renforcerait l'affirmation `fully_warmed` pour les appels externes/réutilisations de wrapper. La valeur `forms` doit rester décrite comme « graphes résidents conformes », non « tentatives ».

P2 — `warmup_cuda_forward_calls` distingue maintenant les appels artificiels, mais `cuda_forward_calls` cumulatif du processus inclut toujours le préchauffage (terrain_server.py:232-238,744 ; terrain_app.py:76-88). Les deltas par tuile, pris après acquisition du verrou GPU, restent utilisables ; les trois warmups internes et la capture de chaque forme ne sont pas des appels Python au wrapper et ne figurent pas dans ce compteur logique. Relier les comparaisons à `capture_calls`, `pool_bytes`, fallback_calls et au temps de startup. Le préchargement ne s'exécute que lorsque terrain_server.py démarre en script, pas lors d'un import WSGI (terrain_server.py:1230-1253).

Les chiffres du prototype communiqués par l'intégrateur, encore distincts du benchmark final, sont : même seed/site isolé 6 508→3 957 ms, préchauffage unique de 4,8245 s, seize graphes retenus, pool base de 675 Mio, sans erreur. Cela suggère un déplacement utile des captures hors du viewport, pas une disparition de leur coût. Attendre le rerun final avec mêmes seeds, fichiers hashés, cache froid, toutes sorties physiques générées, puis mesurer startup + première vue + revisite et VRAM maximale. Aucun résultat n'établit x5.
