REVUE SOL XHIGH 3/3 — APPROVE pour le chemin HTTP actif, sous réserve des reçus finaux en cours

P0 — Aucun défaut bloquant nouveau établi par cette passe en lecture seule. Les routes /height et /tiles demandent toutes deux physical_tile(..., return_arrays=True) (terrain_server.py:923,967) et consomment les arrays rendus ou chargés avec le reçu cohérent. La sortie RAM immédiate ne dépend plus de la fin du writer ; le writer unique garde l’ordre, la capacité est bornée et les abandons/échecs sont exposés (terrain_delivery.py:31-77). Je n’ai lancé ni GPU, ni serveur, ni tests durant cette revue. APPROVE porte sur le code examiné et les contrôles déjà communiqués, pas sur la cible x5.

Correctifs P1 R2 vérifiés. Une preview du conditionnement dont l’état appris est inconnu pendant un verrou GPU occupé est explicitement `provisional=true` (terrain_server.py:488-533). Les réponses preview fixent max-age=0 dans ce cas et imposent must-revalidate ; elles conservent `stage=conditioning-preview` et `source_kind=conditioning-input` (terrain_server.py:991-1010). Le navigateur réinterroge ses previews et vérifie périodiquement la progression coarse (index.html:59,108,130). L’admission d’une nouvelle preview CPU reste réservée à l’état `is False` (terrain_server.py:826). Le test du verrou GPU occupé couvre les headers et l’absence d’attente (test_terrain_navigation.py:568-598).

Les trois remplacements physiques height/climate/reçu sont effectués sous le verrou rayé de la clé, que prend également read_physical_disk pendant les trois chargements (terrain_server.py:783-791,881-891). Le validateur travaille ensuite sur ce snapshot ; les enfants des mips finaux prennent le même verrou (terrain_server.py:469-488). Le test arrête un writer après height et confirme que le lecteur attend puis voit l’ensemble nouveau (test_terrain_navigation.py:599-624). Le job.wait et les contrôles de validité imbriqués restent hors de ce verrou. `X-Terrain-Cache-Source` distingue generated, ram et disk, et le benchmark en compte les occurrences (terrain_server.py:528-533,991-1010 ; benchmark_runtime_navigation.cjs:61). `X-Terrain-Cache` garde sa sémantique historique hit/miss, donc les comparaisons de cache durable doivent employer Cache-Source et un redémarrage.

Le fallback des graphes synchronise le stream, libère les références statiques et le traceback, puis vide le cache avant l’eager après RuntimeError (terrain_cuda_graphs.py:139-154). La branche où la capture dépasse le budget libère également son bucket avant eager (terrain_cuda_graphs.py:124-134). Les tests CUDA indiqués par l’intégrateur couvrent budget zéro, OOM injectée et exactitude de resample ; leur exécution n’a pas été répétée ici. Le budget `TERRAIN_GRAPH_CACHE_MIB` vaut par wrapper, coarse/base/decoder, non pour tout le processus (terrain_cuda_graphs.py:18-23 ; terrain_inference.py:460-471) : avec trois wrappers partagés, 2 Gio chacun par défaut constituent au plus environ 6 Gio de pools comptés, auxquels s’ajoutent poids, activations et autres allocations. L’admission utilise une estimation et la mémoire CUDA libre, avec repli eager si besoin ; ce n’est pas une réservation globale garantie.

P2 — Le contrat legacy `physical_tile(..., return_arrays=False)` reste fragile si la persistance asynchrone est sautée/échoue alors que des fichiers plus anciens existent. Sur hit RAM, `flush()` est suivi du seul test `path.exists() and report_path.exists()` ; il retourne ce chemin avec le reçu RAM sans vérifier le climat ni l’identité/contenu de l’ancien groupe (terrain_server.py:802-809). Un ancien triplet sur disque peut donc être associé au nouveau reçu en mémoire. Dans le chemin après job.wait, la matérialisation synchrone ne se déclenche aussi que si height ou reçu manque (terrain_server.py:905-915). Aucun appel de production trouvé avec `return_arrays=False` ; les deux routes actives utilisent les arrays et échappent à ce défaut. Si cette API doit rester utilisable, relire et valider les trois fichiers sous le verrou puis réécrire synchroniquement les arrays RAM quand le disque ne représente pas ce reçu ; ajouter un test avec `PhysicalDelivery.skipped` et anciens fichiers présents.

P2 — La file de persistance bornée peut omettre une tuile quand ses huit slots sont occupés ; après éviction RAM/redémarrage elle sera régénérée et un mip final exact peut attendre ses enfants LOD 0 (terrain_delivery.py:42-46 ; terrain_server.py:469-485). Les compteurs skipped/failed et les cacheSources rendent ce cas observables, mais la livraison navigateur ne prouve pas la durabilité. Le PNG conserve son ancien couplage de deux remplacements fichier/reçu sans verrou par clé (terrain_server.py:953-986) ; pour les previews, la revalidation navigateur limite l’exposition à une image transitoire, mais une extension future du cache PNG devra traiter cette cohérence séparément.

SNR et mesures. Le chevauchement n’est pas bit-à-bit exact. Le harness courant teste bien `overlap_error<=1` et enregistre `overlap_max_abs_m` (validate_terrain_snr.py:43-54), puis compare le replay strict ; ses SHA concordent avec les sources contrôlées dans le reçu. Le SNR régional effectue aussi des réductions CPU par fenêtre et crée les embeddings à la première politique (terrain_snr.py:22-43 ; terrain_inference.py:165-203) : « aucun forward supplémentaire » ne signifie pas coût nul. Les valeurs de temps des trois profils dans ce reçu sont sensibles à l’ordre de warmup et ne constituent pas un speedup SNR. Le reçu exact-math antérieur compare huit sorties neutres, mais ses hashes ne couvrent pas la totalité des dernières modifications HTTP ; attendre le nouveau reçu final lié aux sources figées.
